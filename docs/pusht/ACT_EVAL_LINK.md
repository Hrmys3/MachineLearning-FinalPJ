# 真实ACT与EvalEnv联通及有界短回合

## 运行入口

策略端`scripts/pusht/checks/serve_act_policy.py`使用固定XPolicyLab真实Model和PolicyServer，读取本机诊断checkpoint与统计量；仿真端`scripts/pusht/checks/check_act_eval_link.py`加载官方push_T/arx_x5布局0，默认通过原生EvalEnv发送一次观测并执行一次返回动作；可显式增加到最多51次。保留原假策略入口，互不替代。

两个终端均从仓库根目录执行。终端A使用已满足ACT/WebSocket服务端依赖的Python，终端B使用已满足Isaac/RoboDojo依赖的Python。先实时检查GPU，分别选两张空闲卡；独立脚本会再次守卫UUID、显存低于10MiB及利用率0。输出目录须不存在。

```bash
nvidia-smi --query-gpu=index,uuid,memory.used,utilization.gpu --format=csv
# 终端A：只监听127.0.0.1，启动后从port.json读取端口
python scripts/pusht/checks/serve_act_policy.py \
  --checkpoint-dir outputs/pusht/act_smoke_20261119_v1 \
  --gpu-uuid <POLICY_GPU_UUID> --output outputs/pusht/checks/act_link_server_new

# 终端B：使用另一张空闲卡，保留物理CUDA/Vulkan编号，勿设置CUDA_VISIBLE_DEVICES
python scripts/pusht/checks/check_act_eval_link.py \
  --device-id <SIM_GPU_INDEX> --gpu-uuid <SIM_GPU_UUID> \
  --port <PORT_FROM_SERVER_PORT_JSON> --output outputs/pusht/checks/act_link_client_new
```

仿真进程结束后，在终端A按Ctrl+C关闭服务并写出服务结果，再检查两张卡释放。服务默认仅接受一次取动作请求，使用`--max-actions`可增加到最多51次，超出上限会被拒绝；不支持直接作为正式批量评测服务。运行期间的状态、图像、预测均只写入本机输出目录。

两端均显式禁用cudnn/matmul TF32，策略端关闭时间集成并从首个预测动作开始。仿真保持CPU物理、显式CUDA规划/相机、dt=.004、25Hz、原生夹爪0到1裁剪与行程映射、关节插值。没有额外动作缩放、臂目标裁剪或专家接管。

## 跨动作块运行协议

复用上述命令和独立的新输出目录，策略端追加`--max-actions 51`，仿真端追加`--steps 51`，两端的动作预算应一致。仍须分别核验空闲GPU，仿真结束后主动关闭策略服务。脚本保留默认单动作模式。

固定布局0、seed0、关闭时间集成、chunk50，每次观测后只执行一个14维动作；保持25Hz、每个动作10次dt=.004的原生物理步。预算51个动作，即2.04秒仿真时间。第1和51次请求应实际运行网络；中间49次从首个预测块取缓存动作。每次仍更新观测，但缓存阶段不会重新使用这些观测生成预测。

服务端通过内部DETRVAE前向钩子记录实际调用次数与输入哈希，逐次核对返回值等于反归一化后的缓存槽位；客户端记录逐步观测、状态、动作、夹爪裁剪与映射、原生控制插值和物理步数。保留第1、49、50、51步前后三路PNG、最终三路PNG及头部视频。视频含初始帧，因此51步对应52帧；25fps文件时长2.08秒，物理推进仍为2.04秒。视频帧率不代表墙钟实时性。

如环境原生终止则提前停止，保留已执行数量，不能跳过终止条件强行凑齐51步。未完成的预算使本次完整51步诊断不通过。此模式仍不支持正式批量评测。

## 验收边界与下一步

这仍是20次更新诊断模型在官方布局0的短回合，不是示范初态回放、600步评测或推动成功率。两条训练示范与布局0不能直接视为匹配初态；关闭时间集成后51次动作仅含2次真正反馈推理。下一步需准备固定预算数据、审计示范与仿真的初态/观测/动作契约，并明确正式训练及完整回合验证协议。正式train20/50、valid20/heldout20和完整成功率仍待完成。
