# 从零理解并跑通机器人 Lift：平台、环境、数据、训练与实验思路

> 面向刚接触机器学习的读者。更新于2026-11-02。本文按“先理解项目，再搭建环境，最后运行与分析”的顺序讲解。实验数据沿用已经核验的本地代码与记录；第9部分是建议工作，不表示已经完成。完整代码留在项目脚本中。

## 1. 我们要做什么——项目大致流程

### 先从一次抓取的全过程想起

假设你站在桌子前，想拿起一个方块。你会先看它在哪里，判断手应该怎样靠近；伸手时，你还会不断观察位置是否正确；碰到方块后，你会收紧手指，再把手抬起来。机械臂做的是相似的事情，只是它不能直接理解“拿起来”这句话，需要程序把这个目标转化为可以计算的观测和动作。

在本项目里，相机图像承担了“看”的一部分作用，关节、末端和夹爪状态告诉程序“自己的身体现在是什么样”。神经网络根据这些信息产生动作，而仿真环境负责执行动作、推进物理过程，再返回新的观测。这个循环持续发生，才构成一段完整的抓取。

因此，项目不是只写一个神经网络。即使网络结构完全正确，只要相机图像上下颠倒、动作的坐标系弄反，或者把下一时刻的状态配给上一时刻的动作，机器人仍然可能抓不到方块。我们要搭建的是一条从数据到动作、再回到观测的完整通路。

读下面的流程时，可以始终带着三个问题：当前这一步需要什么输入？它要产生什么输出？我们用什么现象确认它真的工作了？这样就不容易把“程序没有报错”误认为“机器人已经学会任务”。


这个项目想做的事情很直观：让一只机械臂看到桌上的方块，移动过去，夹住它，再抬起来。

但“让机器人动起来”和“让机器人学会这件事”是两件不同的事情。

我们最先写的脚本，是人规定“先靠近、再下降、再夹紧、最后抬升”。这个阶段没有训练神经网络。后来使用的 ACT，则要从别人成功抓取的记录中学习，在运行时根据图像和机器臂自身状态决定下一步动作。

这里的 ACT 是 Action Chunking with Transformers。先不用记住全名，可以理解成：**它看一眼当前情况，一次预测接下来一小段动作；执行其中一部分后，再看一眼，重新预测。**

我们没有一上来就训练 ACT。因为如果机器人连脚本控制都抓不起方块，那么训练失败时，很难判断是模型没学会，还是环境、夹爪、相机本来就没配置对。

所以实际顺序是：

```text
先让环境运行 → 让相机正常出图 → 用脚本完成抓取
→ 找合适的示范 → 检查示范能否在环境里执行
→ 训练 ACT → 让 ACT 自己控制机械臂 → 查看全部实验结果
```

这条顺序，是理解后面每次选择的主线。
### 先认识三个动作

**采集或获取示范**，是准备“在什么情况下应该怎样操作”的例子；**训练**，是用这些例子调整神经网络参数；**推理**，是固定已训练参数，让模型在新的一轮任务中计算动作。推理时机械臂仍然在动，但通常并没有继续学习。

整个任务的输入是相机图像与机器人自身状态，输出是控制动作。我们最终关心方块是否被抬起、能保持多久、需要多少步，而不只是训练损失下降。

项目可以拆成六个交付物：可运行的Lift环境、可解释的数据来源、正确的数据读取器、适配后的ACT、训练权重，以及含成功和失败案例的评测记录。

## 2. MuJoCo、robosuite、RoboDojo是什么，为什么选择前两者？

### 从“谁负责什么”来区分平台

设想我们要做一个桌面抓取实验。首先要描述桌子、机械臂和方块的形状，还要告诉计算机它们的质量、摩擦和初始位置。但描述完这些，并不意味着它们会运动。程序还必须根据控制输入计算关节和物体下一时刻的位置，并处理碰撞与接触。这部分工作由物理引擎完成。

MuJoCo主要承担物理引擎的角色。如果只有MuJoCo，我们仍要自己组织机器人模型、相机、控制接口和成功判断。robosuite在这些基础上封装出可以直接创建的机器人任务。例如调用Lift，就能得到一个已有桌面、机械臂、方块和评价逻辑的场景。

RoboDojo强调的是另一层工作：组织一系列操作任务，用统一方式运行和评价不同策略。它有自己的仿真与策略接入体系。因此，我们不能因为两个平台都出现了“抓取”或“推动”，就认定它们的数据和接口完全相同。

对刚开始的课程项目来说，最重要的不是选功能最多的平台，而是让必须完成的任务形成一个小而清楚的闭环。我们选择MuJoCo+robosuite，是因为现成Lift任务让我们能先验证一只机械臂、一种物体和一组相机，再逐项加入学习算法。它减少的是项目起步时需要同时解决的问题，而不是消除了所有兼容与训练难题。


### 1. 为什么最后用了 MuJoCo + robosuite？

开始时，我们比较过 MuJoCo + robosuite 和 RoboDojo。对于新人，最容易混淆的是把这些名字都当成“一个机器人软件”。实际上它们负责的事情不完全相同。

| 名字 | 在这个项目里怎么理解 |
|---|---|
| MuJoCo | 负责计算机械臂、方块怎样运动和碰撞的物理引擎 |
| robosuite | 在 MuJoCo 上提供机械臂、夹爪、相机、控制器和任务 |
| Panda | 本次选择的机械臂型号 |
| ACT | 从示范中学习动作的神经网络方法 |
| RoboMimic | 我们最终使用的示范数据来源之一，也提供配套工具 |

我们选 robosuite，最直接的理由是：它已经有 Lift 任务，不需要先自己造一个抓方块的场景。RoboDojo 的运行环境与它不同，我们也没有确认到能直接用于本次作业的标准 Lift 场景和配套示范，因此没有把它作为已经可用的方案。

**本次真正跑起来的系统里没有 RoboDojo 或 Isaac Sim。** 它们出现在前期讨论中，不代表项目用了这些软件。

### 2. 为什么是 Panda？以后可以换吗？

课程没有规定必须使用哪种机械臂。Panda 能完成单臂抓取，而且后面找到的现成 Lift 示范也使用 Panda，因此保留它最省适配工作。

更换场景中的机械臂，和让训练好的模型直接控制另一只机械臂，是两件事。后者涉及夹爪形状、状态表示、动作响应等差异。我们在正式采集、训练前固定 Panda，就是为了避免一边换机器人，一边排查学习问题。
### 它们不是同一层的替代品

MuJoCo是物理计算底座；robosuite在它上面组织机器人任务。RoboDojo则是一套机器人操作基准与评测生态，官方当前仿真端基于Isaac Sim，策略集成主要由XPolicyLab负责。[RoboDojo官方仓库](https://github.com/robodojo-benchmark/RoboDojo)

因此，选择“MuJoCo+robosuite”意味着使用一套配合工作的底座和任务框架，而不是把两个物理引擎叠在一起。参考RoboDojo的任务定义，也不等于运行了RoboDojo官方环境。

对于本次课程项目，我们优先让必做Lift稳定跑通。标准任务现成、Panda与数据匹配、可以逐步检查控制器和相机，这些比平台覆盖多少任务更直接地降低了初期排错难度。这个选择是针对本项目的工作量判断，不是证明MuJoCo在所有任务上都优于Isaac Sim。

## 3. 其他具身相关平台与概念：先把名字放回各自的位置

### 为什么先讲这些名字，而不是直接给下载命令？

新人经常把GitHub仓库、Hugging Face数据集、仿真环境和模型文件看成同一类“项目资源”。如果不区分，后面容易产生这样的误解：下载了示范视频，是否就有训练数据？下载了模型参数，是否就有机械臂环境？答案都取决于文件实际包含什么。

GitHub通常帮助我们取得“程序怎么做”的代码，并查看代码怎样变化。Hugging Face Hub更常用来分发模型、数据与说明，但它同样只是存储和分发资源的平台。我们需要阅读数据卡和文件结构，才能知道下载内容能否接入自己的程序。

一个数据集标记为LeRobot格式，说明它遵循某种字段和索引约定，不代表你必须使用LeRobot的整套训练程序。本次我们读取其中的表格和视频，再转换成自己的HDF5缓存，训练器仍使用适配后的官方ACT。

同样，RoboMimic并不只是一个下载地址。它包含从机器人示范学习的工具和研究数据。我们借用了其示范与环境元信息，但没有因为用了RoboMimic数据，就把学习算法也换成RoboMimic中的另一种模型。数据来源和算法实现可以分开选择，前提是把它们的观测与动作含义对齐。


刚进入具身智能领域，容易一次遇到许多名字。理解它们时，先问“它负责存东西、模拟世界，还是学习动作？”比记住所有名称更重要。

| 平台或工具 | 主要职责 | 我们怎样用它 |
|---|---|---|
| GitHub | 托管代码、记录版本和修改 | 获取官方ACT和robosuite源码，记录ACT提交号 |
| Hugging Face Hub | 托管模型、数据集及相关文件 | 下载社区示范与官方源数据 |
| RoboMimic | 从示范学习的工具与数据生态 | 使用其熟练人类Lift示范和环境信息 |
| LeRobot | 机器人学习工具生态，也定义数据组织方式 | 本次社区数据是LeRobot v3格式；没有直接使用其完整训练器 |
| XPolicyLab | 连接策略实现与机器人评测环境 | 前期了解RoboDojo路线，本次Lift主线未使用 |
| Isaac Sim | 机器人仿真平台 | 用于理解RoboDojo技术路线，本项目没有安装运行 |

Hugging Face是数据获取平台，不是物理仿真器，也不是某一种神经网络。下载一个数据集，不会自动创建机械臂环境。我们用`huggingface_hub`从它获取文件，在本机用PyTorch训练、用robosuite执行。[Hub官方说明](https://huggingface.co/docs/hub/en/index)

### 后面反复出现的词

- **具身智能**：智能体通过身体或执行器与环境交互。本项目的“身体”是仿真Panda。
- **策略（policy）**：把观测变成动作的规则或模型；脚本专家和ACT都是策略，但实现不同。
- **模仿学习**：从示范学习动作。本次主线属于模仿学习。
- **行为克隆**：把示范里的观测和动作当作监督学习样本；ACT也在学习这种映射，同时引入动作序列和潜变量结构。
- **强化学习**：主要依据交互奖励学习策略。本次没有通过强化学习训练机器人。
- **episode/轨迹**：从一次重置到这一轮结束的整段交互记录。
- **step/控制步**：一次动作输入及环境推进；20Hz表示每秒20个控制步，不等于程序实际运算一定实时。
- **闭环**：执行后重新观察再决定下一步；长时间不看新状态地执行预先给定动作则更接近开环。
- **benchmark/基准**：一组任务、数据和评价规则。只有保持协议一致，结果才有比较意义。
- **checkpoint/权重文件**：保存模型学到的参数，可能附配置；是否能恢复训练还取决于是否保存优化器等状态。

HDF5、Parquet和MP4是文件格式，不是学习算法。HDF5适合按组保存数组；Parquet适合表格字段；MP4存相机视频。一条训练示范可能同时分布在这些文件里，需要用episode和时间索引对齐。

## 4. 环境、示范与参考资源：数据从哪里来？

### 一条能用于学习的示范，具体应该包含什么？

如果你只拍摄机械臂抓取的视频，人可以看懂，但网络并不知道每帧对应哪个控制指令。因此，本项目所需的数据不是单纯的“成功视频”，而是按时间配对的图像、机器人状态和动作。

例如，在第t步，我们先保存相机看到的画面和机械臂当前状态，然后保存接下来要执行的动作。动作执行后，物理环境发生变化，下一次得到的是第t+1步的观测。这个先后顺序必须保持一致，否则网络会学到错误的对应关系。

环境数据又是另一回事。机器人和桌子的模型文件、质量和摩擦参数、相机的位置与朝向，决定了这个世界怎样运行、画面怎样产生。它们通常不是用来逐帧监督网络的动作标签，却会影响同一套动作能否产生相同结果。

所以我们下载了两种互补资源：社区转换版方便读取图像和状态；官方源文件帮助恢复原来的模型与物理初态。只看一份“有图像、有动作”的字段列表还不够，我们还需要确认这些动作能在当前环境中实际完成抓取。



先区分三种“数据”，否则很容易把下载环境资产误认为已经获得训练示范。

| 类型 | 包含什么 | 本项目来源 |
|---|---|---|
| 环境模型与配置 | 机器人、桌面、方块、相机、控制器、物理参数 | robosuite的Lift及模型文件；源示范中的环境元数据 |
| 训练示范 | 每一步图像、自身状态与专家动作 | Hugging Face上的RoboMimic PH社区转换版 |
| 回放与初态信息 | 模型XML、初始物理状态、原始动作 | 官方RoboMimic Lift源HDF5 |

robosuite的标准Lift是“可交互的任务”，不是一个训练好的ACT，也不保证附带所有训练图像。机器人、方块和评价逻辑先准备好，再选择示范来源。[标准任务说明](https://robosuite.ai/docs/modules/environments.html)

### 4.1 我们曾经尝试自己生成示范，为什么中途改变路线？

#### 1. “环境”和“示范”分别提供什么？

robosuite 的标准 Lift 给我们场景、机器人、控制接口和成功判定。它相当于准备好练习场地，但不等于自动把教学记录也交给我们。

一条训练示范要告诉 ACT：**当时看到了什么、机器人处于什么状态、接下来执行了什么动作。** 只有屏幕录像，没有动作记录，不够直接训练这里的 ACT。

#### 2. 自采路线是怎样形成的？

脚本抓取稳定后，我们自然想到：既然脚本会抓，就把它每一步的观测和动作存下来，让 ACT 学它。

`collect_lift.py` 按以下时间关系记录：

\[
 (I_t,s_t)\longrightarrow a_t\longrightarrow(I_{t+1},s_{t+1}).
\]

也就是先记录执行前的图片和状态，再记录这一步要执行的动作。不能拿执行后的图片，去配执行前的动作。

但是保存到第 39 条时，进程出现 `corrupted double-linked list` 和 `Aborted`。已保存的 39 条通过了结构和数值检查，但原计划没有完成，也没有采到验证集。

这是底层内存错误，日志不足以确认具体哪个库造成。没有证据证明是内存不足，也没有完成根因修复。

#### 3. 为什么决定转向 PH 数据？

用户重新问：**为什么一定要自己生成？Hugging Face 上不是已经有数据吗？**

这次回看发现，自己采集不是 PJ 的要求。早期其实已经找到 RoboMimic PH，但在脚本成功后，助手把“验证专家”继续推进成“必须自采”，没有及时重新比较成本。

于是主线转向现成数据：高质量人类示范已经存在，先用它跑通 ACT 更合适。脚本专家仍证明了环境能完成任务，但自采的 39 条没有进入当前模型训练。

这也是项目规划中的一个重要取舍：**已经投入时间，不等于必须继续沿那条路线走。**

### 4.2 最终使用的开源示范与兼容检查

我们选择了社区转换版 `chaoqi-liu/robomimic_mt4_ph`，它来源于官方 RoboMimic 熟练人类示范 PH。

- 社区版提供两路图像、机器人状态和动作，方便训练。
- 官方 `demo_v15.hdf5` 提供环境配置、每条示范的模型和仿真状态，方便恢复初态和检查动作。

两份数据分别解决不同问题，而不是重复下载。

#### 1. 我们实际用了哪些数据？

这个社区数据集有四个任务，共 800 条。Lift 对应 task_index=0、episode 0–199，共 200 条、9,666 帧，平均每条约 48 帧、2.4 秒。

只用 Lift 训练；视频文件合并存储，因此下载文件里包含其他任务，不代表把其他任务加入了训练。

| 内容 | 具体含义 |
|---|---|
| 双相机 | 第三视角 agentview、腕部 robot0_eye_in_hand |
| 图片 | 256×256 RGB，20 Hz |
| 状态9维 | 末端位置3 + 四元数4 + 夹爪位置2 |
| 动作7维 | 位置增量3 + 旋转增量3 + 夹爪指令1 |
| 控制约定 | 世界坐标系 OSC_POSE |

自采数据也是9维状态，但它存的是关节位置和夹爪位置。**数字一样，不代表意思一样。** 所以不能直接混在一起训练。

#### 2. 为什么先回放动作？

如果示范动作放进当前环境根本抓不起来，那么 ACT 即使把这些动作学得很像，也可能失败。

我们从官方文件恢复三条示范的模型和初态，执行原始动作，三条都成功。这里发现了一个容易漏掉的设置：源环境使用 `lite_physics=False`，实际评测也保留它。

三条回放的最大关节位置偏差约为 0.00425、0.00376、0.00697。这不是完全一致的数值回放，但能完成任务。该偏差混合不同关节坐标，不能统一解释成米。

#### 3. 图像、动作也分别核对了

首条社区示范与官方动作最大差异只有约 3×10^-8，两路视频均读出59帧，人工查看正常。

在线推理时又用同一初态的训练首图作对照，确认两路实时图像都需要上下翻转。翻转后的误差远低于原图，机器人状态差异也只有约3×10^-8。

这些核对解决的是：模型训练时看的东西，与运行时看到的东西是不是同一种表示。不能仅因为图像尺寸、动作维数相同，就认为对接完成。

### 4.3 划分、统计与缓存怎样准备

我们按整条示范划分，而不是把相邻帧随机拆到训练和验证两边。否则同一次抓取前后几帧太相似，验证容易变成见过的画面。

划分种子固定为42：

| 划分 | 数量 | 已完成内容 |
|---|---:|---|
| 训练池 | 160条 | 固定编号 |
| 20条训练子集 | 944帧 | 实际用于当前模型 |
| 50条训练子集 | 2357帧 | 已准备，包含前述20条；尚未训练50条模型 |
| 验证集 | 20条、954帧 | 用于离线误差与闭环检查 |
| 保留集 | 20条 | 未用于当前评测 |

训练50条候选数据加验证20条，共70条已转换为逐轨迹HDF5缓存，全部通过读取检查。缓存让训练不用反复定位长视频。

状态与动作的不同分量尺度不同，所以用训练集均值和标准差处理：

\[
 \tilde s=(s-\mu_s)/\sigma_s,\qquad
 \tilde a=(a-\mu_a)/\sigma_a.
\]

运行时把预测动作变回来：

\[
 \hat a=\tilde{\hat a}\sigma_a+\mu_a.
\]

标准差至少取0.01，避免很小的数放大噪声。统计量只从对应训练子集算，不借用验证数据，也不使用整个四任务数据集的统计量。

## 5. 跑通项目需要哪些框架、系统环境、包与工具？

### 5.1 Linux是什么？Ubuntu又是什么？

操作系统负责管理计算机硬件、进程、文件、内存和程序运行。我们平常使用的Windows是操作系统；Linux相关系统也承担类似职责，只是内核、软件组织方式和使用习惯不同。

严格地说，Linux首先是一个操作系统内核。内核之外还需要命令行工具、软件包管理器、系统库等，才能组成日常可用的系统。Ubuntu是把这些组件组织在一起的一种Linux发行版。因此，“安装Ubuntu”和“使用Linux环境”在日常交流里经常一起出现，但Ubuntu不是唯一的Linux发行版。

许多机器人与深度学习项目首先提供Linux安装说明，使用Bash脚本和Linux软件库。选择Ubuntu的目的，是让我们的运行方式更接近这些项目文档，而不是因为所有机器学习都必须在Linux上进行。

### 5.2 如果电脑是Windows，为什么还会出现WSL？

WSL是Windows Subsystem for Linux的缩写，即Windows上的Linux子系统。它允许我们在Windows电脑里运行Linux发行版，而不必每次切换到另一套系统。WSL2使用真正的Linux内核，在受管理的虚拟化环境中运行，并与Windows集成。

安装WSL2后，Windows没有消失。你仍然可以使用Windows的浏览器和编辑器，同时在Ubuntu终端里运行Python和Linux命令。这里存在两套路径和软件环境：Windows里的Python，不会因为你在Ubuntu里输入`python`就自动成为同一个解释器。

Ubuntu中的`/home/用户名/`是Linux用户目录，`~`表示当前用户的家目录。Windows磁盘通常可以在WSL里通过`/mnt/c`、`/mnt/d`等路径访问。反过来，Windows也能通过WSL共享路径查看Linux文件。但文件可以互相看到，不等于两边安装的软件包自动共享。

如果你已经在原生Linux或云服务器上工作，就不需要再安装WSL。WSL是Windows用户进入Linux工作流的一种方式，不是MuJoCo或ACT的必选依赖。[微软WSL说明](https://learn.microsoft.com/en-us/windows/wsl/install)

### 5.3 终端、Shell和Python分别在做什么？

终端是输入文字命令、查看程序输出的界面。Shell负责理解命令并启动程序，例如Ubuntu中常见的Bash、Windows中的PowerShell。Python则是我们运行机器人与训练代码的解释器。

因此，`cd`、`ls`通常由Shell处理；`python train_act_lift20.py`表示让Shell启动Python，再由Python执行脚本。`import torch`是Python语句，不能直接当作Bash命令运行。

终端提示符中的`(ml)`通常说明当前激活了名为ml的Conda环境，它不是代码的一部分。复制教程命令时，不要把提示符一起复制进去。命令块标为PowerShell时应在Windows终端执行，标为bash时应在Linux终端执行。

### 5.4 Conda环境为什么有必要？

假设一个项目需要较旧的MuJoCo，另一个项目需要较新的版本。若都安装在同一套Python里，更新一个项目可能破坏另一个项目。Conda环境让我们为不同用途准备不同的Python和依赖集合。

激活环境后，`python`和`python -m pip`应该指向这个环境。我们使用`which python`和`python -m pip --version`检查实际路径，避免把包安装到另一套解释器中。`base`是Conda的基础环境，不建议把所有项目依赖都堆进去。

不必为每一次小实验都新建环境。已有环境如果版本合适、依赖没有冲突，可以复用；如果里面承载其他重要项目，或者版本约束明显不同，就更适合另建环境。选择依据应该是检查结果，而不是环境名字。

### 5.5 PyTorch、torchvision、GPU和CUDA怎样配合？

PyTorch是本次训练神经网络的核心框架。它提供张量计算、神经网络层、自动求导和优化器。模型先给出预测，损失函数衡量预测与示范的差异，自动求导计算参数应如何调整，优化器再完成一次更新。

GPU适合并行处理大量数值计算。CUDA是NVIDIA GPU计算的软件体系，PyTorch的相应构建利用它执行运算。显卡驱动负责底层访问；PyTorch包通常携带或依赖运行所需的计算库。是否需要额外安装完整CUDA Toolkit，取决于是否编译自定义扩展等具体需求，不能看到GPU就先把所有CUDA组件都装一遍。

在WSL2中，NVIDIA GPU支持依赖Windows侧驱动。不要照搬原生Linux显卡驱动安装步骤，把Linux显示驱动装进WSL来替代Windows驱动。[NVIDIA WSL指南](https://docs.nvidia.com/cuda/wsl-user-guide/index.html)

`nvidia-smi`能看到显卡，只是第一层证据。`torch.cuda.is_available()`检查PyTorch能否访问CUDA；真正执行一次GPU运算，则进一步验证计算链路。相机OpenGL渲染又是另一条链路，所以GPU训练正常时，相机仍可能报错。

torchvision提供ResNet18等视觉模型与图像工具。我们使用ImageNet预训练权重作为图像编码器起点，让模型利用已经学到的视觉特征。它不是预训练好的Lift策略，机器人动作仍需要通过本次示范学习。

### 5.6 仿真、控制与渲染需要哪些组件？

MuJoCo负责物理演化，robosuite负责组织Lift任务与机器人接口，OSC_POSE控制器把末端位姿指令转换为机器人执行所需的控制。模型输出的七个数不是“直接给每个电机多少力”，而是控制器定义的一组位置、旋转和夹爪输入。

Mink是逆运动学相关依赖。本次Panda路径没有使用其全身IK功能，但它的版本约束仍会影响安装。Numba和llvmlite用于部分数值加速，SciPy的Rotation帮助处理姿态。

渲染负责从相机角度生成图像，物理仿真负责物体怎样运动。可以先不生成相机图像，仅检查机器人动作；这样一旦出错，更容易分清是物理还是图形问题。`MUJOCO_GL`用于选择MuJoCo的图形后端，不是选择CUDA版本。

### 5.7 数据、日志和版本工具各有什么用？

| 工具 | 在本项目中的用途 |
|---|---|
| NumPy | 数值数组、归一化统计与数据拼接 |
| h5py | 读写HDF5轨迹、模型与仿真状态 |
| PyArrow | 读取Parquet表格和episode索引 |
| OpenCV | 解码MP4视频，将BGR转换成RGB |

这些工具各自解决一个小问题。训练器不是单独读取一个“数据集对象”就自动理解全部含义，而是通过这些组件把图像、状态和动作整理成PyTorch张量。日志和版本记录则帮助我们在结果变化时追溯原因。

### 5.8 把整个软件层次串起来

```text
计算机硬件：CPU、内存、磁盘、GPU
    ↓
操作系统：原生Linux，或者Windows中的WSL2 Ubuntu
    ↓
Python运行环境：Conda或venv管理解释器和依赖
    ↓
两条主要工作链：
  MuJoCo + robosuite → 模拟机器人与相机
  PyTorch + torchvision → 训练和运行ACT
    ↓
项目脚本 → 读取示范、发送动作、保存日志和评价结果
```

理解这几层以后，就可以按层排错：命令不存在先查系统与PATH，包导入失败先查Python环境，张量不能上GPU再查PyTorch与驱动，场景报错查仿真，图像报错查渲染，抓取效果差再查数据、控制和学习问题。

## 6. 如何从已有的任意环境开始检查并搭建运行环境？

这一节不假设读者已经有Ubuntu、Conda、GPU版PyTorch，或者某个特定用户名。目标是先识别当前起点，再进入一条明确的Linux运行路线。它不是保证所有操作系统、硬件和版本都能使用完全相同命令。

先约定：Windows用户使用WSL2 Ubuntu路线；已经在原生Linux或Linux服务器中的读者跳过WSL安装。macOS用户可以检查并运行部分仿真功能，但不能直接使用这里的NVIDIA CUDA路线；若希望尽量复现实验的GPU训练与仿真组合，可以使用合适的Linux机器。无GPU时仍可先检查数据与部分仿真，但不能把CPU速度等同于本实验条件。

### 6.1 第一步：确认自己当前在哪个系统里

如果正在Windows PowerShell中，先执行：

```powershell
wsl --status
wsl -l -v
```

第二条会列出已安装的Linux发行版，并显示使用WSL1还是WSL2。已经有可用Ubuntu且VERSION为2时，不要重复安装。可以用`wsl -d`进入列表中实际存在的发行版，名称以自己的输出为准。

如果已经在Linux终端中，执行：

```bash
cat /etc/os-release
uname -r
pwd
```

第一条识别发行版，第二条识别运行内核，第三条显示当前目录。内核名包含WSL相关字样时，说明这里是WSL中的Linux；普通Linux服务器通常不包含这些字样。

如果Windows尚未安装WSL，先按[微软官方安装说明](https://learn.microsoft.com/en-us/windows/wsl/install)检查系统前提。在管理员PowerShell中查询可用发行版，再选择安装，例如：

```powershell
wsl --list --online
wsl --install -d Ubuntu-22.04
```

安装过程可能要求重启，并在首次启动时创建Linux用户名和密码。示例选择22.04是为了接近本项目验证路线，不代表其他版本一定不可用。已经安装其他合适发行版时，先检查兼容性，不必为了名字一致就重装。

### 6.2 第二步：检查计算与存储资源

进入Linux后执行：

```bash
free -h
df -h .
nvidia-smi
```

内存决定可以同时放多少数据和运行多少进程；磁盘用于存放代码、视频、缓存和模型；GPU显存用于模型训练以及部分图形资源。三者不能互相替代，磁盘很大不表示显存足够。

如果不是NVIDIA GPU，`nvidia-smi`不存在是预期情况之一，不应据此安装NVIDIA驱动。如果机器确实有NVIDIA GPU但命令失败，则先检查驱动与系统集成，再处理PyTorch。

原生Linux应按机器和发行版配置相应驱动；WSL2应优先检查Windows侧驱动与WSL支持。不要把这两条路线的驱动安装命令混用。云服务器还需要确认当前实例真的分配了GPU，而不仅是名称中提到GPU。

### 6.3 第三步：检查现有Python和环境管理工具

```bash
command -v conda
command -v python
command -v python3
```

如果安装了Conda，再查看：

```bash
conda --version
conda info --envs
```

如果存在可能适合的环境，先激活它。下面的名字只是示例，应替换成实际环境名：

```bash
conda activate existing-env
python --version
which python
python -m pip --version
python -m pip check
python -m pip show numpy torch torchvision mujoco robosuite mink
```

`Package(s) not found`意味着某些包还没安装，不等于整个环境不可用。`pip check`只能检查已声明的依赖关系，不能证明所有原生库和运行路径都正常。

判断能否复用时，要同时看Python版本、PyTorch与torchvision是否配套、仿真依赖约束，以及这个环境是否还承担其他重要项目。不要为了接入机器人库，随意降级一个已有项目依赖的NumPy或PyTorch。

### 6.4 第四步：没有合适环境时，创建独立Python环境

如果有Conda，可以创建一个新环境：

```bash
conda create -n lift-act python=3.11 pip -y
conda activate lift-act
```

环境名可以自行选择。这里用Python3.11作为与本项目运行版本接近的起点；最终仍需核对所选PyTorch等包的支持范围。

如果没有Conda，也可以选择安装Conda发行版，或者使用系统提供的Python3与venv。venv路线示例：

```bash

python3 -m venv ~/venvs/lift-act
source ~/venvs/lift-act/bin/activate
python --version
```

如果提示没有venv组件，在Ubuntu中可安装`python3-venv`；其他发行版使用相应包管理方法。venv继承创建它的Python版本，不会自动变成3.11，所以必须检查实际版本。使用Conda与venv二选一即可，不要无意中层层嵌套。

激活环境后，再确认`which python`和`python -m pip --version`都指向预期位置。除非有清楚理由，不使用`sudo pip install`安装项目依赖。

### 6.5 第五步：检查或安装匹配的PyTorch

已有PyTorch时，先测试，不要先重装：

```bash
python - <<'PY'

print("PyTorch CUDA runtime:", torch.version.cuda)
print("CUDA available:", torch.cuda.is_available())
if torch.cuda.is_available():

```

如果包不存在，或当前构建不适合目标硬件，请根据[PyTorch官方安装选择器](https://pytorch.org/get-started/locally/)选择操作系统、包管理器与计算平台，并安装配套的torch和torchvision。为本项目不需要仅为了音频而安装torchaudio。

不要把`nvidia-smi`显示的CUDA能力数字直接照抄成安装包后缀，也不要在GPU版不可用时用CPU版替代后误以为已经完成GPU配置。二者都能运行部分Python代码，但训练条件不同。

安装后重新执行GPU测试，再验证torchvision可导入。若报缺少算子或二进制接口错误，应先检查torch与torchvision配套关系，而不是继续往环境中叠包。

依赖中会涉及NumPy、SciPy、OpenCV、Pillow等。新增依赖是否与已有版本兼容，要看实际解析与运行，不应强行对任意环境套用本人的完整包列表。

再进行导入检查：

### 6.7 第七步：确定项目目录，再测试物理与相机

在Linux用户目录中创建项目目录，例如：

```bash

cd ~/robotics/lift-project
```

这个路径是示例，不要求与原作者用户名和目录相同。项目脚本大量使用相对路径，所以运行前要进入包含脚本、data和third_party的项目根目录，而不是在任意目录启动。

WSL用户可以把代码放在Linux文件系统中工作；Windows编辑器通过WSL连接打开它。这样可以减少跨文件系统大量读写的不便。不要因为能在Windows中看到文件，就默认Windows Python会使用WSL的Conda环境。

将项目脚本放到根目录后，先执行无相机测试：

```bash

```

它通过后再执行相机测试：

```bash

```

目前我们亲自验证的是WSL图形环境下的GLFW路线，并未证明所有EGL或软件后端在任意机器上都通过。通用教程应该告诉读者如何选择分支，而不是假装所有图形环境相同。

### 6.8 第八步：保存自己的版本记录，并明确通过标准

```bash
python -m pip freeze > requirements-current.txt
python -m pip check
```

## 7. 环境搭好后，怎样从零一步步跑整个流程？

### 先学会怎样阅读一次运行结果

这一节的每个脚本都承担一个明确的检查任务。运行前先确认自己知道它在测试什么。例如，零动作脚本里机械臂不抓取是预期行为；随机张量模型测试里损失很大也不奇怪，因为输入没有真实任务含义。

运行结束后，可以把结果分成三层。第一层是程序是否正常完成；第二层是数据和数值是否符合约定；第三层才是机器人是否完成任务。这三层依次通过，才能减少“程序运行成功，所以实验成功”的误判。

遇到报错时，优先保留完整Traceback、当前命令和版本，不要一口气修改控制器、相机和依赖。一次只改变一个有根据的因素，才知道修复究竟由什么带来。下面保留了我们的实际探索过程，最终主线与历史分支会分别说明。



这一部分不是要求把每段历史都重新跑一遍。脚本专家和自采属于探索分支，最终训练主线使用PH数据。每一阶段都给出“在回答什么问题”，便于出错时停在正确位置。

### 7.1 先验证环境和脚本抓取，而不是直接训练

#### 1. 最小测试为什么用零动作？

`test_lift.py` 只检查场景能否加载、重置和执行动作。它没有抓取策略，所以奖励为 0 是正常的。方块高度先下降一点再稳定，是物体落到桌面的过程。

之后 `test_lift_camera.py` 检查相机。我们确认原始图片倒置，上下翻转后能正确看到桌面、机械臂和方块。

```bash
python test_lift.py
MUJOCO_GL=glfw python test_lift_camera.py
```

先不打开相机、再打开相机，是为了把物理运行问题和图像问题分开。

#### 2. 第一版脚本怎样抓？

我们让脚本读取方块真实位置，按固定阶段移动：

| 阶段 | 控制步数 |
|---|---:|
| 到方块上方 | 100 |
| 下降 | 100 |
| 闭合夹爪 | 30 |
| 抬升 | 120 |
| 保持 | 30 |

总共 380 步，20 Hz 下约 19 秒。它不是最短路径，而是优先求稳、方便看清动作。

移动时根据“目标位置减去当前位置”的误差产生动作：

\[
 e_t=p^*-p_t,\qquad u_t=\operatorname{clip}(6e_t,-0.6,0.6).
\]

这里 p* 是想去的位置，p_t 是当前位置。误差大就多动一点，误差小就少动一点，再限制最大输入，避免一次给出太大的指令。这些是归一化控制输入，不是直接移动多少米。

第一版三个初态都成功。但 GIF 让用户发现了数值看不出的细节：**夹爪不转，有时沿着方块对角线抓，可能容易掉。**

#### 3. 用户的观察怎样改变了设计？

我们没有直接猜一个转腕角度，而是先打印方块和末端的姿态，确认参考坐标系。然后让末端朝下，并从正方形四个等价方向里，选一个离当前姿态最近的方向。

姿态控制可以简写为：

\[
 e_R=\operatorname{Log}(R^*R_t^\top),\qquad
 u_R=\operatorname{clip}(0.8e_R,-0.15,0.15).
\]

不用先掌握矩阵细节也能理解：R* 是希望达到的朝向，R_t 是当前朝向，这个计算给出“还应往哪个方向转多少”。同一轮抓取中目标朝向固定，避免夹住后还追着方块姿态转来转去。

修改后，三个初态下降前的误差只有约 0.13°–0.15°。随后在种子 1000–1049 的 50 个初态中，三项脚本指标全部通过，首次原生成功平均在第 234 步。

注意：脚本的“稳定抬升”是相对初始方块中心升高至少 10 cm、连续 10 步；后来 ACT 的“连续成功”是连续满足环境原生条件。这是两个不同标准。

#### 4. GIF 为什么一开始是静态的？

保存参数误写成了 `append_image`，正确名称是 `append_images`。后来又出现修改了一个脚本、实际运行另一个脚本的问题。加入实际保存帧数检查后，确认抓取动画有约 191 帧。

这次问题不是机器人没动，而是展示文件没更新。排查时先确认“运行的是哪个文件、保存了几帧”，比先怀疑物理仿真更有效。

### 7.2 让官方ACT适应我们的机器人

官方代码最初针对双臂任务，多处写死了14维。我们的状态9维、动作7维，不能把所有14简单改成同一个数字。

`adapt_act.py` 保留原始仓库，复制出 `third_party/act_lift`，分别修改：

- 状态投影层：接收9维。
- 动作编码层和输出层：接收/输出7维。
- 视觉骨干：使用当前 torchvision 的权重接口。

固定的上游提交为：

```text

```

然后用真实数据训练100次更新，检查数据读取到保存模型的整条路径。通过后才开始2000次候选训练。这种顺序让问题尽量在小规模时暴露。

### 7.3 从小训练检查到候选模型

#### 1. 训练配置与直观解释

| 配置 | 值 | 怎么理解 |
|---|---:|---|
| 训练示范 | 20条 | 模型学这些成功操作 |
| batch size | 8 | 每次更新看8个训练起点 |
| 更新次数 | 2000 | 反复调整网络参数的次数 |
| 动作块 | 20步 | 每次预测未来约1秒动作 |
| 视觉骨干 | 预训练ResNet18 | 利用已有图像特征，不全从零学习 |
| 图像输入 | 双路128×128 | 原始256×256统一缩小 |
| Transformer宽度 | 256 | 网络内部表示维数 |
| 编码/解码层数 | 4/4 | 本次固定的模型规模 |
| 注意力头 | 8 | 内部注意力配置 |
| FFN宽度 | 1024 | 内部网络配置 |
| 主体/骨干学习率 | 1e-4 / 1e-5 | 骨干更新得更慢 |
| 优化器 | AdamW | weight decay=1e-4 |
| 梯度裁剪 | 1.0 | 限制过大的梯度 |
| 随机种子 | 42 | 固定本次实验随机设置 |

图像转到[0,1]，再用ImageNet均值和标准差归一化。无额外数据增强。脚本中的 `num_epochs=1` 只是上游参数占位，真正执行的是2000次更新，不能写成“只学一遍”。粗略算，2000×8=16000次样本使用，约为944个训练起点的17遍量级。

#### 2. 损失在教什么？

主要一项是预测动作与示范动作的距离：

\[
 L_{L1}=\frac{\sum m\,|\hat a-a|}{\sum m},\qquad
 L=L_{L1}+10L_{KL}.
\]

m表示这个位置是否有真实示范。示范尾部不足20步就补齐，但补齐部分不算动作误差。KL项来自ACT的条件变分结构，约束潜变量分布；不能把它直接理解成“机器人成功率”。

训练时网络能借助真实未来动作学习潜变量；验证和执行时没有未来动作，采用z=0。

#### 3. 已完成训练结果

| 实验 | 验证归一化L1 |
|---|---:|
| 无预训练骨干，100次更新流程检查 | 0.61277 |
| 预训练骨干，2000次更新候选 | 0.47361 |

候选最后一个训练批次：L1约0.2809、KL约0.0093、总损失约0.3738。实际PyTorch峰值显存约481.3MiB；这不是仿真和其他进程的总显存。

两次实验训练时长也不同，因此不能说差异全由预训练带来。保存的是最后一步模型，不是定期验证选出的最佳模型；checkpoint没有优化器状态，也不是完整断点续训文件。

### 7.4 第一次闭环为什么能成功？

第一次闭环时，模型在验证episode57里很快抓起了方块。这不是“没怎么训练就神奇成功”：前面已经花了大量工作把环境、图像、状态、动作约定对齐，训练也进行了2000次更新。

几个有利条件同时存在：任务短且集中；示范是熟练人类操作；预训练骨干提供视觉特征；双相机和自身状态提供反馈；模型每执行少量动作就重新观察。

这些解释有道理，但没有消融实验，不能证明某一项单独贡献最大。

同时要澄清：脚本专家的姿态对齐没有直接传给这个ACT。当前ACT学的是PH数据，推理时也没有专家替它算动作。

## 8. 现在的进展与遇到的问题

### 怎样读懂“已经跑通”和“仍有问题”同时成立？

模型已经能在许多初态下接近、闭合夹爪并抬升，这说明数据到控制的链路确实工作了。但“工作了”不是“已经足够可靠”。持续执行时夹爪可能张开，有些初态也可能没有正确夹住方块。

所以本节不只给一个平均数字，而是分别看曾经成功、连续一段时间成功和最后仍成功。三个指标是在问不同问题，不应该挑最高的那个代替整个系统的表现。我们也把用户对GIF的观察保留下来，因为日志会漏掉动作姿态与接触过程中的细节。


### 8.1 已经跑通了什么

环境、双相机、Panda脚本抓取、现成数据兼容检查、70条缓存、官方ACT适配、20条候选训练、20初态验证和GIF总览均完成。自采数据与50条数据准备也有保存，但它们不等于已经训练或评测了相应模型。

### 8.2 抓起来后掉落：从现象到日志

#### 1. 是谁决定执行这么久？

第一次脚本持续运行200步，即10秒。不是模型自己决定“我要执行10秒”，而是程序不断调用模型：

\[
 \text{观察}\rightarrow\text{预测20步}\rightarrow\text{执行前5步}
 \rightarrow\text{再观察}\rightarrow\cdots
\]

三个长度要分清：20是预测长度，5是重新观察前的执行长度，200或100是整个评测时限。环境参数horizon=250也不是当前实际运行时限；真正起作用的是外层 `while step < 100`。

#### 2. 用户观察推动了日志设计

用户看到：先抓得很顺，保持一段时间后突然掉下，并指出示范并没有覆盖这么长的后续时间。

我们于是补充逐步日志，不再只看最后一个成功布尔值。日志记录每步实际夹爪指令、夹爪位置、方块高度、末端位置和连续成功步数。

episode57的200步诊断显示：

- 第38步首次成功，约1.9秒。
- 第47步确认连续10步成功。
- 第38–198步连续成功，共161步、约8.05秒。
- 第153步起有负夹爪指令，先开合交替，后持续张开。
- 第194–199步，开度代理量从约0.045增到0.072，方块从约1.090m降到0.807m。

因此这条轨迹不是“始终夹紧但突然滑落”，日志支持张开指令与掉落有关。但开度只是两关节坐标差的代理量，不是抓力传感器，不能排除运动和接触的共同影响。

#### 3. “短示范导致长期保持不足”是结论吗？

它是合理假设。示范平均约2.4秒，在完成附近结束；运行却持续5或10秒。补齐位置又没有损失监督，所以网络没有被明确教会后面应一直夹紧。

但还没有对照实验证明它是唯一原因。五步动作块中还出现了周期性开合，闭环误差也可能让模型进入不熟悉的状态。

我们讨论过补充保持示范、缩短执行块和增加规则，但这些没有成为已经完成的实验，当前结果也没有夹爪锁定规则。

### 8.3 从单次成功到全部验证结果

#### 1. 为什么改成100步？

用户建议先固定100步，也就是5秒，建立基线。单个episode57在100步结束时成功，看起来抓取流畅。

这里必须诚实记录：这个时限是在看到200步后期掉落后确定的。缩短时限没有改变模型能力，只改变了评价窗口。

#### 2. 为什么还要看20个初态？

单次顺利不能代表所有情况。我们按固定验证划分跑20个初态，每个初态一个独立进程，降低长时间反复创建图形资源的影响。20个进程全部完成，没有执行异常。

三种结果分别回答不同问题：

| 指标 | 问题 | 结果 |
|---|---|---:|
| success_any | 有没有哪一步达到环境成功条件？ | 19/20，95% |
| stable_native_success_10_steps | 有没有连续0.5秒达到条件？ | 19/20，95% |
| success_final | 第100步还成功吗？ | 3/20，15% |

首次成功平均41.947步，约2.10秒，仅对19个至少成功一次的样本统计。

**“95%成功”单独写会误导。模型大多能完成短期抬升，但5秒末保持成功只有15%。** 原生条件主要依据任务高度，不直接证明方块一直被稳固夹住；坠落途中仍可能短暂满足高度条件。

#### 3. 用户再次纠正了失败分析

最初讨论偏向“都在最后松开”。用户查看其他GIF后指出：也有一开始就没有夹住的情况。

因此不能把全部失败统一解释成后期松开。实际数据中，episode102从未达到原生成功；另有16条先成功后结束失败。视觉上某阶段抓空，是否后来恢复、何时失去接触，不能只靠三个布尔值判断。

这是我们制作4行×5列同步GIF的原因：把所有情况放在一起，避免只挑一个顺滑成功案例形成印象。

### 8.4 已完成工作中仍需注意的限制

当前结果来自一个训练种子、20个同分布验证示范初态。保留集尚未评测；100步预算是在观察200步掉落后确定的，具有探索背景。

自采进程的堆内存错误没有定位根因。每初态独立进程后20轮无异常，是当前运行事实，不能据此证明底层问题永久修复。

没有完成20/50条训练对照，没有执行长度对照，也没有做视觉骨干、相机数量的消融。因此，“为什么效果好”的解释只能作为有依据的分析，不能写成逐项验证的因果结论。

## 9. 接下来还应该做什么？

### 为什么下一步不是直接把训练次数翻倍？

如果问题来自输入方向错误，多训练只会更充分地学习错误关系；如果问题来自没有保持阶段监督，多训练现有短轨迹也不一定产生保持能力。因此，后续应先提出可以被实验区分的解释，再决定增加什么数据、改变什么配置。

每个对照尽量只改变一个因素，并使用同一组验证初态。比如比较执行1步与5步时，不同时换一份训练数据；比较20条与50条时，不把验证规则也改掉。这样即使结果没有提高，我们也能解释实验究竟排除了什么可能。

下面列出的工作是建议顺序，不是已经取得的结果。保留集只有在方法选择结束后才用于最终评价，避免反复根据测试结果修改系统。


后续工作应先解决“结果能否解释和比较”，再扩大训练规模，而不是看到掉落就盲目增加训练轮数。下面按建议顺序展开；这些尚未完成。

### 9.1 先固定原始基线，再给失败分类型

保留当前20条模型、划分、100步预算和全部日志，不覆盖它们。把失败按动作过程归类：没有对准、夹爪闭合时没夹住、抬升途中滑落、成功后张开、其他。

分类依据应是GIF和CSV共同提供的证据。`success_any`与`success_final`只说明是否满足环境条件，不能独自回答夹爪有没有接触方块。这样能避免把所有失败都归为短示范问题。

### 9.2 做一个不需要重新训练的小对照

同一个checkpoint、同一组验证初态，比较每次执行1步、5步、10步后再观察。预测块仍保持20，其他设置不变。

这个实验回答：五步块内的开合波动，是否与执行方式有关？如果更频繁观察改善结果，它说明闭环执行设置值得关注；并不证明数据没有问题。

### 9.3 针对“保持不足”补充真实监督

从训练示范恢复环境并回放，确认抬升后，追加2–3秒真实保持段。保持控制应让末端位置和朝向稳定，夹爪持续闭合，记录每步实际图像、状态和动作。

不要只复制最后一帧：物体仍在仿真中运动，图像与接触会变化。新增片段必须通过成功与不掉落检查。仅扩展训练示范，不把验证示范动作拿来训练。

再比较原始示范与增加保持段的ACT。示范条数仍可记为20条，但必须报告新增帧数与监督时长，说明训练数据变多了。这才能检验“短示范缺少长期保持监督”的假设，而不只是口头认定它正确。

### 9.4 完成课程要求的20/50条对照

我们已经有嵌套子集和各自统计量。训练50条模型时，应统一模型结构、预训练来源、数据处理、验证规则、执行长度与评测初态。

还要说明公平预算采用什么口径：相同更新次数意味着计算量接近，但50条每条被重复看的次数更少；相同遍数则更新次数更多。两种口径都可以解释，但不能不写。

正式训练可加入定期验证和最优checkpoint保存，并保留最后一步权重。当前候选只保存最后一步，不应误称最优模型。

### 9.5 把“完成Lift”和“长期保持”分开评价

保留固定100步结果，同时明确连续成功10步、最终成功、首次成功步数的定义。若另做成功即停止的评价，应单独报告，不与固定时限末成功混用。

可以增加较长时限作为保持能力测试，但应提前固定规则。若为了演示加夹爪锁定，也应标成“ACT+规则”，不能冒充原始ACT自然学会保持。

### 9.6 冻结方法后再使用保留集

验证集用于发现问题、选择配置。方法确定后，再在保留集上一次性报告结果，避免反复看测试结果调参。必要时增加训练种子，报告结果波动与置信区间。

需要特别注意：当前缓存只有训练50条和验证20条。保留集虽然已划分，但没有被同样缓存；当前图像方向诊断又依赖初态对应的缓存首图。最终评测前，应把方向约定固定下来，避免把诊断工具隐含依赖带到正式测试。

### 9.7 补齐工程复现与交付

整理最终环境锁定信息，去掉不可移植的本机路径，固定数据版本或哈希。保存下载与预处理配置、训练参数、上游版本以及修改说明。

当前checkpoint没有优化器状态。若需要可恢复训练，应保存优化器、更新步数和随机状态。报告里保留成功与失败案例，说明AI辅助使用环节与成员贡献。

课程还有可选扩展时，再评估Push-T任务与数据适配的工作量。RoboDojo可以提供参考，但不应在Lift的稳定性问题尚未解释清楚时，把现成Push-T视频误当成可直接训练的数据方案。
